Issue body

it would be cool if after I start a new project on my laptop, and use the button in braska to init a git repo, I could then turn the repo into a GitHub repo from inside brisk too. it should ask which account I want to create it on, what the name of the repo should be, if it should be public or private, and anything else you can think of that makes sense.

Chosen approach

Two entry points feed one "Publish to GitHub" modal (renderer/publish-modal.js). Entry point 1: after git:init succeeds in git-changes.js, immediately open the modal — the highest-signal moment, no detection work needed. Entry point 2: add hasRemote to the git:status response (a pure local read of .git/config via git remote, no network), then render a "Publish to GitHub" journey card whenever a git repo has no remote. The modal collects: repo name (pre-filled from folder basename), owner (personal account + orgs via new gh:list-accounts handler), visibility (private by default), and optional description. On submit, gh:repo-create calls gh repo create <owner>/<name> --source . --remote origin [--push], skipping push if the repo has no commits yet. This mirrors VS Code's "Publish Branch" and GitHub Desktop's "Publish repository" patterns.

Assumptions

  • The installed gh CLI supports gh repo create <owner/name> --source <path> --remote origin --push (available since gh v2.4).
  • Org repos are created using <org>/<name> as the positional argument to gh repo create (not --org flag).
  • gh api /user/orgs?per_page=100 returns all orgs the authenticated user belongs to (same pattern as gh:list-repos).
  • Adding a single git remote call to git:status is acceptable latency — it reads .git/config locally, no network, same order as other status checks already done there.
  • If the user has no commits yet, gh repo create --source . --push fails. We assume detecting this via git rev-parse HEAD and omitting --push is the right fallback (create the remote but let the user push manually). Human should verify this is the desired UX.
  • Default visibility should be private (matching GitHub Desktop). Human should confirm this matches the product expectation.

  • Visibility defaults to private; user can toggle to public.
  • Description field is optional.
  • If the repo has no commits, publish succeeds without a push and the user sees an informational message.
  • Auth errors surface a message pointing to gh auth login.
  • node --test passes with new tests for gh:repo-create and gh:list-accounts.

Decisions

2026-05-19Used <owner>/<name> positional arg format for gh repo create rather than a --org flag — works for both personal accounts and orgs, consistent with how gh documents its API.
2026-05-19Added hasRemote (bool) to git:status via a cheap git remote call (reads .git/config, no network) rather than isGitHub (which would require a gh repo view network call). The journey card fires on any no-remote repo, not just ones whose remote points to github.com.
2026-05-19Used native alert() for the no-commits-after-publish case (low-frequency, non-blocking). If this proves janky, a showChangesStatus call would be cleaner but requires threading the dep into the modal.
